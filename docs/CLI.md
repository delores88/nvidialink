# Agent and human CLI

For additional Linux/WSL computers, named-device selection, first GPU preparation and qualified job IDs, see [Multiple compute computers](MULTI-DEVICE.md). Existing commands below retain their legacy Spark/laptop behavior when no additional profiles are registered.


`sparkdev` never prompts, invokes a pager, allocates a TTY, or interpolates workload arguments into SSH shell text. `--json` produces structured output. Attached runs stream JSON log events followed by the final result; detached commands return one JSON object. Client labels support accounting and fairness; they are not evidence that a particular AI agent actually ran a command.

## Offload by default

Use the installed CLI and owner-state path from **Agent setup**. Check `devices` and `status --all`, then send Linux-capable builds, tests, rendering, media conversion and compute through `run --where auto --detach`. Keep Windows/MSVC work on the laptop through its configured build gate. Retain the request ID and returned job ID, use bounded `wait` and incremental `logs`, and inspect the final workload exit code. Report an unavailable scheduler rather than silently bypassing it.

The 0.5.0 candidate returns Spark job files automatically. There is no required fetch step: keep waiting while `state` is `returning`. The CLI, controller and installed Windows return worker must all be updated together. Source tests are separate from physical Spark transfer/render/package tests, installed Windows behavior and Marketplace acceptance; this page is the usage contract, not a receipt for those checks.

## Setup and state

Run setup with your existing SSH alias and pinned `known_hosts` identity. All identifiers below are examples, not owner configuration.

```powershell
sparkdev setup --ssh-alias my-spark --host 192.0.2.10 --host-key-alias pinned-spark --identity-file C:/Users/You/.ssh/spark --user owner --local-build-gate C:/path/to/buildlock.py --json
sparkdev doctor --json
```

The key path is referenced, never read, copied, or uploaded by DGXBridge. OpenSSH performs authentication in BatchMode with strict known-host verification. Setup, connection changes and a Find my Spark save all write the configuration under one lock, so two of them running at once never overwrite each other.

LAN connection order: within one command, an address that already authenticated is reused. If that sticky address becomes unreachable before authentication, DGXBridge clears it and makes one full plan. With automatic addresses enabled (the default), saved `--host` order takes precedence over stale remembered successes. Authenticated Spark route hints then rank wired addresses before unknown media and Wi-Fi, with faster reported link rates first and equal rates retaining saved order. This is a link-rate hint, not a throughput promise. With `connection --auto-addresses off`, the earlier remembered/configured/alias planning remains available.

Only a successful authenticated `status`, `doctor`, `devices`, or `connect` may refresh route hints. A changed `network.lan_epoch` or a report older than 24 hours triggers one `lan_routes` request, with a 60-second retry cooldown. `run`, `prepare`, `sync`, `logs`, `wait`, and `cancel` never learn routes. The reply is bounded to eight canonical RFC1918 IPv4 addresses; at most three additional on-network learned candidates are planned. A local UDP route lookup sends no packet. Learned-only addresses require an open SSH port check and then the same strict host pin; they never enter saved configuration or `lan-route.json`. Their pre-authentication failures cannot produce exit 7 or block the paired fallback; a confirmed changed host key suppresses the hint for six hours for that laptop source address. Timeouts and failures after authentication stop as before. A success is recorded only in `lan-learned.json`.

When learned hints participate, parallel probes share a result board. An earlier pending probe becomes `Late` after 300 ms if a later candidate is already open. The plan is never reordered by probe timing: an earlier configured host is held back and still dialed before a later pre-authentication rejection can end the request. A learned-only address is never dialed with unchecked reachability. The original strict authentication, post-authentication retry boundaries, and configured-host rejection behavior still apply.

Before dialing, when more than one address is planned, every concrete address gets a parallel TCP check of the SSH port (1.5 s per connect, 2 s overall). A single planned address, unless learned-only, is not checked: nothing could be dialed ahead of it, so it gets exactly the dial it had before rediscovery. An address that refuses, stays silent for the whole 1.5 s, or whose name resolves to nothing is reported as `host_unreachable` and held back. A held-back `--host` address keeps its place ahead of later addresses: it is dialed once more before a later address's failure that ran nothing remotely (a rejection or another failure before authentication) can end the command, and before giving up. That dial uses a 3 s connect timeout, what the 2 s check left of the 5 s each `--host` address had before rediscovery, so the check plus that dial never cost a dead address more than its one dial did, and a slow host the check missed still gets its own dial. A held-back alias `HostName` that is not a `--host` value is not dialed. When nothing answers, a command therefore costs no more than the serial dials before rediscovery, plus the local `ssh -G` lookup. A check that runs out of time, such as a slow name lookup, decides nothing: that address is dialed in order with OpenSSH's own timeouts. A command returns as soon as it has its answer and never waits for slower checks. When the alias uses ProxyJump, ProxyCommand, BindAddress or BindInterface, or `ssh -G` fails, nothing is checked locally, because ssh reaches every address through that route. An answering port is only a candidate: it must still pass the same pinned host-key check and key authentication.

Every dial runs OpenSSH with `LogLevel=VERBOSE`, which writes its "Authenticated to" line to stderr once key authentication succeeds and before the remote command starts. That stderr is read only to classify the result and is never shown or stored. Only lines OpenSSH writes itself count: before the host key is checked, a device answering on the SSH port can echo its own banner, disconnect text or algorithm list into stderr, and none of that text decides anything. Only OpenSSH's own failure (exit 255) can mean an unreachable address or a dropped connection; a remote command's own exit status never does, whatever it printed. An ssh exit 255 with no output and without that line ended before authentication; anything else may have run the command. Before authentication, connection refusal, timeout, DNS failure or an unreachable network moves to the next address.

A dropped connection counts as dropped during the handshake, with nothing run remotely, when neither the "Authenticated to" line nor any output came first, whether or not OpenSSH tags it with the identification exchange (`kex_exchange_identification`, `ssh_exchange_identification` or `banner exchange`). A drop after that line or any output, including an untagged "Connection reset by" or "Connection closed by", which OpenSSH prints the same way in every phase, may have run the command. A command repeats at most one dropped dial, at the same address with the identical pinned command, after a pause of 1 to 1.5 s: a handshake drop for any request, and any other drop only for requests the Spark controller treats as the same request when repeated (`status`, `logs`, `wait`, `doctor`, `cancel`, the sync and upload steps, laptop lease heartbeats and releases, a `resources` read, and run, prepare and claim requests with a request ID). A raw desktop command, a resource policy write or an unknown request is repeated only after a handshake drop. A deadline set when the request starts bounds this: after any drop each later dial must end by it, and neither the repeat nor another address is dialed without enough time left (10 s, plus the server-side wait a `wait` request asks for). Authentication failures, timeouts and process errors are never repeated. A drop that may have run the command ends the command at that address with exit 4 and no fallback, and the address stays remembered; the message says that the request may have run and whether it is safe to repeat, and for run and prepare it names the request ID to reuse. A handshake drop moves to the next address and keeps a remembered address; when nothing else serves the command, it fails with exit 4 and, like unreachability, allows remote fallback.

At a `--host` address, or at the alias when no `--host` is set, an authentication or host-key error ends the command with exit 7 and prevents remote fallback, and any other failure before authentication, such as an incompatible SSH server, ends it with exit 4, as before rediscovery; held-back `--host` addresses ahead of it get their dial first, and later addresses are not tried. A remembered address is only a learned hint. If it rejects the pinned host key or the login, or answers with an incompatible SSH server, it is forgotten and the next address is tried through the same pin; a dropped connection or a timeout is no evidence that it is stale and never forgets it. When that address is a `--host` value, a rejection still prevents remote fallback: the command fails with exit 7 unless another address authenticates. The alias's own `HostName` was not dialed before rediscovery when `--host` values are set, so any failure there that ran nothing (a rejection, an incompatible server, a handshake drop, too many authentication failures, or a transport timeout whose stderr shows it never authenticated) is reported in `attempted_routes` and the next address is tried; it never turns an otherwise unreachable result into exit 7. For every address, a failure after authentication, a remote command's own failure, a drop that may have run the command, or any other transport timeout stops at once without fallback. Configured and alias addresses that authenticate are remembered in `lan-route.json` in the state directory: at most eight, four per SSH alias, pin, port and user. Each expires 30 days after it last authenticated; an address in daily use is re-verified in the file at most once a day. Route memory is not written when the state folder is redirected or its redirection cannot be determined. Automatic rediscovery never rewrites `config.json` and never scans the network; only the owner's Find my Spark action below searches, and only when asked.

## Find my Spark (owner only)

```powershell
sparkdev --client human --json discover
sparkdev --client human --json discover --save ADDRESS
```

The desktop's **Find my Spark** button runs these for the owner. They run only with exactly one explicit `--client human` (or `--client=human`) before any `--`; a bare call, `--client claude`, `--client codex` or a repeated `--client` is refused with exit 2. That check is advisory, like every client label: labels are self-declared, so it prevents an accidental run, not one by a misbehaving agent with a shell. They are not MCP tools, and nothing runs them automatically: not `devices`, `status` or `connect`, not the desktop refresh, and not an unreachable-LAN error. Disconnected and Remote-only refuse them with exit 4, as they refuse SSH.

`discover` searches only this laptop's own networks, and only on Windows. It uses Ethernet and Wi-Fi hardware adapters that are up, are not tunnels or filters, and have a connector, a default gateway and a preferred RFC 1918 IPv4 address; a Hyper-V virtual switch or a VPN adapter is skipped. Each address's network is clamped to its /24 (a /25 to /30 stays as it is, a /31 or /32 is skipped), at most two networks are searched, and a wired and a Wi-Fi adapter on the same network are merged. An address is kept only when Windows routes it out of one of that network's own adapters, so a VPN that claims private ranges never carries the search. Each kept address gets one TCP connect to the configured SSH port (3 s each, 4 s overall). At most 32 answering addresses (configured addresses first, then the alias's `HostName`, then ascending) are checked, 16 at a time, with the same pinned `ssh` command every dial uses (BatchMode, `StrictHostKeyChecking=yes`, `HostKeyAlias`, never `accept-new` or a known_hosts write) running `true`, 8 s each. The alias must reach the Spark directly: ProxyJump, ProxyCommand, BindAddress or BindInterface refuses the search with exit 4, as does a failed `ssh -G`. Because a `Match host` block can route a single address differently, each answering address is also looked up with `ssh -G` and the pinned check's own arguments first; an address that would go through a proxy, jump host or bind option, or whose lookup fails, is counted as `not_direct` and never checked. The whole search takes up to about 25 seconds.

The result lists only the addresses that passed the pinned host key and login (`found`, each with the laptop adapter that reached it), the status of every configured address and of the alias's `HostName`, and counts: `open`, `unchecked` (its port check could not finish in time), `not_checked` (answered beyond the 32), `login_rejected`, `local_key_error`, `other_ssh_hosts`, `unknown_key_hosts`, `unverified` (answered on the SSH port, but the pinned check broke off, timed out or was disconnected by the server) and `not_direct`. Other devices appear only as counts. A changed host key counts as another device only when the same search proved the pin, through an address that authenticated or whose server refused the login after the host-key check; otherwise it counts as an unknown key, and `pin_hint` suggests checking the pinned known_hosts entry. A local key or SSH configuration error never proves the pin, and neither does any text the answering device sends before the host-key check. The adapter and `medium` describe this laptop's side only. `spark_kind`, `speed_mbps`, and `hint_learned_at` are separate Spark-side hints from a recent authenticated route report, or null when unknown/stale. Verified results are ranked by those hints; `recommended_host` and `preselected` identify the first result without saving it. A laptop wired adapter alone never labels the Spark wired. `discover` writes nothing.

`discover --save ADDRESS` takes a private IPv4 address on one of those networks and routed through it, checks it again together with up to 15 configured addresses on the same networks, and saves nothing unless it authenticates: a host-key, login or local key failure is exit 7, and no answer, or an address your SSH settings route through a proxy, jump host or bind option, is exit 4. It then makes the canonical address the first `--host` under the configuration lock, keeps every other address except configured ones this check proved to be another device, and names those in `removed`; an address that is closed, unchecked or answers with an unknown key is kept. When no `--host` was set, the alias's own route stays as the second address: its `HostName`, or the alias itself when it has none, so that address keeps the dial and the fail-closed result it had as the only route. If the alias, pin, port, user, key file, connection or mode changed during the check, it writes nothing and asks for a new search (exit 4). Like setup it refuses a redirected state folder, or one whose redirection cannot be determined (exit 3). The saved address is also remembered in `lan-route.json`, and more than four saved addresses add a `warning`.

`--allow-remote` explicitly permits the separately paired `sparkdev-link` transport after LAN reachability fails. Pair through the desktop QR workflow after SSH bootstrap. No owner-operated relay is assumed.

State defaults to Windows LocalAppData plus `SparkDevBridge`, and `~/.local/state/sparkdev` on Linux. `SPARKDEV_HOME` overrides the shared CLI/link state root. Configuration, pairing identity, receipts and logs stay outside the repository. Do not point state at a source tree. SSH bootstrap separately installs the controller under `~/sparkdev`.

Windows packaged applications can redirect AppData file I/O even when the known-folder API returns the normal owner's path. `connection` reports the configured and physically resolved state roots, package context and redirection. Setup refuses a detected redirected folder. Use the desktop's generated agent prompt/MCP snippet to select the verified owner state; do not copy keys or silently create a second configuration. No automatic config-only migration is performed.

## Connection and resource controls

```powershell
sparkdev --json connection
sparkdev --json connection --mode lan-only
sparkdev --json connection --mode remote-only
sparkdev --json connection --mode both
sparkdev --json connect
sparkdev --json disconnect
sparkdev --json resources
sparkdev --json resources --file C:/settings/spark-limits.json
sparkdev --client human --json resources --internet off
sparkdev --client human --json resources --internet on
sparkdev --json connection --laptop-jobs 2
```

LAN-only uses pinned SSH. Remote-only skips SSH and requires existing authenticated pairing; it does not guarantee iroh uses a relay. Both prefers LAN and falls back only after reachability failure. Authentication or host-key rejection never falls back. Connect enables the saved route and probes it; a failed probe leaves the configured choice enabled and returns a failure. Disconnect blocks new requests without revoking pairing or cancelling admitted jobs. Existing laptop workers retain their connection snapshot for lease heartbeats.

`resources` reads physical Spark bounds and effective policy. The JSON file is an object with `cpu_per_job`, `memory_gb_per_job`, `cpu_total`, `memory_gb_total`, `client_jobs`, `client_cpu` and `headroom_gb`. Saving validates relationships and hardware bounds, persists the controller policy, and returns the effective readback. Changes govern new requests/admissions; running jobs retain their original resources. After the first explicit policy save, project overrides are clamped to saved per-job caps. Default laptop concurrency is two and can be changed separately. Laptop native CPU and memory caps are not enforced by this release.

In the 0.4.1 candidate, Spark job internet defaults to on. `--internet on|off` changes the owner policy independently of the numeric caps; turning it off also removes running jobs' public-network helpers on the next scheduler tick. Job status distinguishes enabled, disabled, cut by owner and unavailable helper access. Public access uses HTTP/HTTPS proxies and blocks private/home networks, the Spark and cloud metadata; it is not unrestricted raw TCP/UDP access. A missing helper or failed guard leaves a job offline, with that limitation visible. Dependencies prepared through `prepare` retain their fixed allowlist. Ask the owner before changing their internet or resource policy. Internet changes and saved-download mutations require exactly one explicit `--client human` argument; agent tools remain read-only for these settings. This label is an accidental-use guard, not an authentication boundary.


## Submit, poll and reattach

```powershell
sparkdev --client codex --json run C:/work/project --where spark --runtime rust --detach --request-id build-001 -- cargo test --locked
sparkdev --client codex --json wait JOB_ID --timeout 20
sparkdev --client codex --json logs JOB_ID --since 0
sparkdev --client codex --json logs JOB_ID --since NEXT_OFFSET
sparkdev --client codex --json status --all
sparkdev --client codex --json cancel JOB_ID
```

Use the returned `next_offset` for subsequent logs calls. Offsets count bytes, and `data` is base64 for lossless retrieval; `text` is a UTF-8 presentation. Every captured chunk is saved locally at its original byte offset. Log queries are repeatable. An attached run passes through the workload exit code; its JSON contains `process_exit_code`. Detached submission, wait and logs return success for a valid operation even if a completed workload failed: inspect `state` and `exit_code`.

Reuse the same `--request-id` after an ambiguous submission disconnect. The immutable request is saved before network submission and cannot be reused for different source, argv, runtime or placement. Without an explicit ID each new invocation is a new request. A connection failure (exit 4) of a Spark run or of prepare ends its message with the request ID, including a generated one, so it can be reused. No-cache controls result reuse, not request identity. Run requests survive laptop disconnection once accepted by the Spark; cancel requests made offline are queued and delivered at the next authenticated command.

## Placement and shared board

`sparkdev devices --json` reports the laptop's observed OS, architecture and process-visible logical parallelism, local job receipts, and the authenticated Spark scheduler board, limits and configured runtimes. Unreachable or unconfigured Spark state carries an explicit error. Logical parallelism and scheduler limits do not indicate idle processors or free memory; those values remain unknown. Device inspection does not reserve capacity or deliver queued cancellations.

The Spark device's `network` is the controller's link report (see "Network link report" in the remote controller docs): `{v:1,observed,basis,active,underlay,wired,wired_up,wired_lan_up,wifi}`. `null` means there is no report: the Spark is unreachable or unconfigured, its controller predates the report (a bridge repair adds it), or the report's `v` is not 1. `{"v":1,"observed":false,"basis":"unknown"}` means the controller answered but could not observe its own link. `basis` says how `active` was found: `ssh_session` (the interface that owns this SSH connection), `default_route` (the lowest-metric default route, as for paired-route requests) or `unknown` (no default route). The report holds no SSID, BSSID, MAC or IP address; MAC-derived interface names appear as aliases such as `usb-ethernet-1`. Additive fields keep `v:1`. It is observation only and never changes route choice, fallback or admission.

Spark `availability` is `reachable`, `unreachable` or `unconfigured`. Transport `route` is `lan_ssh`, `paired_iroh` or `none`, with `authenticated` and bounded `attempted_routes` explaining LAN reachability errors, authentication rejection, disabled/unconfigured remote access or adapter failure. Each LAN attempt names its `source` (`sticky`, `remembered`, `configured` or `alias`) and the dialed `host`, which is null when OpenSSH resolved the alias. Its `status` is `authenticated`, `host_unreachable`, `authentication_failed`, `connection_dropped`, `ssh_command_failed` (an incompatible SSH server, or a failure with no evidence of anything else), `transport_timeout` or `process_error`. There is one record per dial, plus one for each address the precheck held back. A `connection_dropped` record adds `phase` (`handshake`: before authentication, nothing ran; `session`: the command may have run), `try` (1, or 2 for the repeat) and `retry` (`scheduled`, `exhausted`, `not_safe_to_repeat` or `insufficient_time`); any other record of a repeated dial carries `try: 2`. A Spark `error` from a dropped connection has `kind` `connection_dropped`. `target_index` is the position of the dialed address among the configured `--host` values, whatever its source, and null when the address is not one of them. An authenticated LAN route reports the dialed address as `lan_host`. The paired route does not claim that iroh used a relay or a direct connection; the adapter does not report that physical path. A completed strict SSH exchange followed by controller failure remains visible as authenticated transport with a controller error. Authentication rejection never triggers fallback.

Laptop process availability is separate from managed admission. Both runners need the shared Spark scheduler: when it is unreachable or unhealthy, `can_submit:false` and `admission.available:"unavailable"` disclose that dependency even though the laptop itself is available. When the scheduler is healthy, `can_submit:null` and `admission.available:"requires_request_check"` mean that runtime, quota, resource and worktree checks are still needed. There is no automatic offline laptop fallback or platform-incompatible rerouting.

`sparkdev plan DIR --where auto --runtime rust -- cargo test --locked` previews the same placement policy used by run. `--argv-json FILE` is also supported. Planning validates the source and exact arguments, computes the manifest without writing transfer objects, and returns `admission_required:true`, `claimed:false`, `uploaded:false` and `submitted:false`. It needs no network or SSH configuration. The result is a preview, not a reservation; run revalidates the tree and runtime against current scheduler admission. Runtime availability is not verified by plan.

`--where auto` chooses the laptop for explicit Windows/MSVC targets, PowerShell/cmd scripts, Windows sandbox commands, NSIS tools and Tauri installers. Other work goes to the Spark. Use `--where laptop` or `--where spark` when the command has requirements the classifier cannot infer. The selected machine and reason are included in submission output. Runtime defaults are `rust` for cargo/rustc/rustup, `node` for node/npm/npx, `cuda` for direct ffmpeg/blender commands and `python` otherwise; `--runtime` selects only an owner-provisioned registry name. Request `--runtime cuda` explicitly for GPU Python. A CUDA runtime does not make arbitrary code use the GPU: select the supported encoder, Blender device or ML backend in the workload. Read observed `gpu_video` capabilities rather than assume an encoder name proves hardware acceleration.

The laptop runner executes native owner processes and is not Docker-sandboxed. It obtains the same worktree lease from the Spark scheduler before starting, so it requires an authenticated scheduler connection. Laptop concurrency follows the saved owner setting (default two). Direct Cargo invocation is wrapped in the configured build gate, with per-project CARGO_TARGET_DIR under application state. On this owner's machine all local Cargo commands must use the prescribed PhaseForge build gate unchanged, and state/build output must stay on C:. Commands that indirectly invoke Cargo must themselves use the owner's build gate; the CLI cannot inspect arbitrary script behavior.

Laptop workers persist independently of the invoking CLI. On Windows they launch without inheriting the caller's capture pipes, run at lower process priority, send a shared-board heartbeat every 15 s, counted from the start of the previous one so a slow heartbeat is followed at once by the next, and stop their owned process tree on cancellation or a lost lease (no successful heartbeat for 45 s). An expired laptop lease remains blocking on the scheduler because a sleeping laptop may resume a process. This protects the worktree from a second job; explicit terminal acknowledgement releases it. Final laptop log/board updates interrupted by a disconnect are saved and retried at the next authenticated command. `status --all` returns scheduler jobs plus laptop receipts and indicates unavailable remote state. Jobs for distinct worktrees may run independently on both machines. Laptop successful-result caching is disabled because the native host toolchain has no locked digest. Spark result reuse is scoped to the same worktree and requires matching source, exact argv, pinned runtime, worker and resource policy, including network mode. Different worktrees keep separate build caches and completed results; 0.4.1's `/cache` downloads are shared across worktrees. `--no-cache` forces a new execution but keeps using those saved downloads.

## Automatic returned files (0.5.0)

Normal Spark batch jobs return newly created and modified regular files from `/work` to their original project-relative paths. Files written under `/sparkdev-output` instead arrive under `results/JOB_ID` in the local owner state directory; `results_folder` reports the full path. Use that output directory for videos, renders, reports and other deliverables that should not replace project files. Logs are independent and remain available through `logs`. Native laptop jobs already write locally; services use their separate `call` response protocol.

Only files are returned; remote deletions do not delete laptop files. Rebuildable/control directories such as `target`, `node_modules`, `dist`, `build`, virtual environments, Python caches, `.git` and bridge state are excluded. Put a deliverable in `/sparkdev-output` if its normal build folder is excluded. Secret/key paths, links and unsafe destinations are refused. Return filters cannot recognize every possible secret; never put credentials in results.

A changed work file replaces its original only when the laptop copy still matches the uploaded hash. A newer local edit is kept, and the Spark file becomes a sibling such as `report.spark-JOB_ID.txt`. If that sibling already contains different bytes, it is preserved and the return reports an error. Safe replacement can leave a hidden `.report.txt.spark-original-JOB_ID-UUID` backup of the prior file; these backups are currently retained for recovery, not automatically deleted. Review conflicts and backups before removing them yourself.

The detached `sparkdev-return` worker resumes transfers after the submitting agent exits, with one worker per owner state. The ordinary Windows installer registers a logon dispatcher; it resumes this install's known state directories with explicit `--state-dir` paths, including custom `SPARKDEV_HOME` locations. The credential-free path list lives in `%USERPROFILE%/.dgxbridge/return-workers.json`; both that location and each configuration are physically checked to refuse package redirection. Packaged CLIs do not write logon registry entries. Pending transfers resume when the laptop is awake, signed in and the saved bridge connection is enabled and reachable. An update stops this worker to replace its executable and preserves its receipts, configuration and admitted jobs; the updated worker resumes from those receipts. Uninstall removes the app's logon entry but retains the path list for reinstall. This candidate behavior still requires installed Windows acceptance.

`wait`/`status` expose `returned` entries (`path`, `source_path`, `scope`, `bytes`, `sha256`, `status`), `results_folder` and `return_status` (`pending`, `retrying`, `complete` or `disabled`). While delivery is incomplete, a terminal remote workload is presented as `state:"returning"`, with its original `workload_state` and exit code retained. `return_error` explains failures; they remain retryable rather than becoming false success. Completion requires verified chunk and whole-file hashes and acknowledgement of the exact manifest. Failed/cancelled jobs can also have useful files to return. Cached successful jobs reuse retained immutable files as well as logs.

```powershell
sparkdev --client codex --json outputs JOB_ID
sparkdev --client codex --json run C:/work/project --where spark --detach --no-return --request-id keep-remote-001 -- python3 task.py
```

`outputs` is optional manifest/receipt inspection, not a download step. `--no-return` explicitly disables automatic return for that run. The result limits are 64 GiB per file and per job, 10,000 files and a 3 MiB manifest. Split oversized results into separate jobs. Unacknowledged frozen files are retained for seven days; after every receiver acknowledges delivery, retention becomes one day. Cache reuse can extend the expiry. `outputs.retention.expires_at` is authoritative; expiry and later housekeeping apply only to frozen result copies, not source snapshots or job logs. Locally returned files/receipts have no automatic expiry. After remote expiry, rerun the workload with a new request ID when files must be recreated.

## Saved downloads

The 0.4.1 candidate keeps model and package downloads in `/cache`, shared by all Spark jobs. Download normally, retain the default cache settings and put large reusable files in `/cache/files`. Tokens remain under the job's `/tmp`; executable extension/module caches and large temporary files are private to each job. Locked preparation has a separate `/prepare-cache`, so arbitrary run jobs cannot poison its pip download cache.

```powershell
sparkdev --client codex --json downloads
sparkdev --client human --json downloads --keep-gb 200
sparkdev --client human --json downloads --free-up
```

Any client can read usage. Only `human` may change the keep limit (20 GiB up to disk size) or request clearing; client labels are attribution, not an extra authentication boundary. Clearing is accepted while jobs run, reported as `clear_pending`, and performed when jobs finish and Docker confirms no Spark job container is running. Clearing is not an MCP tool. The default keep budget is 200 GiB; automatic eviction uses an idle-only 48-hour last-use threshold and targets 90% of the budget while keeping a 128 GiB disk floor where old eligible downloads allow it. This conservatively protects downloads used in the last day on relatime filesystems. Recently used content can keep the cache over budget. Status uses the latest bounded measurement, never a new recursive scan on every request; unknown or incomplete usage is not a fresh capacity promise.

The internet switch does not isolate this shared cache. Every Spark job belongs to the same owner's trust domain and can change its contents. Never put credentials or private account configuration there. See [controller details](REMOTE.md#saved-download-storage).

## Named model services

`serve DIR --name NAME -- CMD ARGS` starts a Spark-only HTTP service and returns a job receipt. `call NAME --body-json TEXT` sends JSON; `--input FILE` sends bytes, and `--save FILE` saves the checked response. The option is `--body-json` because global `--json` controls CLI output. Logs, wait and cancel accept a server name; cancellation by name requires a live connection and is never queued for a later, potentially different server. The complete example, limits, durable request IDs and reply handling are in [SERVERS.md](SERVERS.md). These commands require the 0.4.1 CLI and controller candidate; old controllers ask for a Spark setup update.

## Sync and locked dependency preparation

```powershell
sparkdev sync C:/work/project --check --json
sparkdev sync C:/work/project --json
sparkdev prepare C:/work/project --runtime rust --json
```

Sync checks every included file before network upload. Git inventory includes tracked and untracked non-ignored files. Plain directories use a guarded walk. Build outputs, symlinks/reparse points, paths outside the root, credential/key names, secret directories and recognizable credential contents are refused or excluded. Source files named `secrets.rs` are permitted; actual credential-shaped content is not. This is a conservative safety filter, not a guarantee that arbitrary unknown secret formats can be detected. Transfer uses verified SHA-256 1 MiB chunks; retries upload only missing objects. Deleted files disappear in the next immutable snapshot.

Files are streamed: each is read once in 1 MiB chunks, hashed per chunk and whole, and scanned with 64 KiB of look-ahead across chunk boundaries, so memory use does not grow with file size. A file whose length changes while it is read is refused with exit 3 ("retry"). A project may hold files of up to 16 GiB and 32 GiB in total, of which files of 512 MiB or less may total 8 GiB; at most 100,000 files. `sync --check` reports `bytes`, `small_bytes`, `large_files` and these `limits` without writing transfer objects. Files of 512 MiB or less are staged in the local transfer store only while at least 4 GiB of laptop disk stays free; larger files, and any chunk missing from the store, are read again from the source at their offset and verified against the manifest hash ("Source changed during sync; rerun" if they differ).

A sync first asks the Spark which limits it advertises. A controller that predates this release advertises none, and then any file over 512 MiB or project over 8 GiB is refused before upload with "update Spark setup"; redeploy the controller through the desktop setup. A current controller is asked to commit first, so an unchanged project needs two requests. Missing chunks are uploaded in first-occurrence order, in batches of at most 8 MiB over LAN SSH and 3 MiB over the paired route, in at most three rounds. A batch is halved for the rest of the sync when it proves too slow: a transport timeout, or on the paired route the sidecar failing because the Spark cut off a request that took over 10 seconds. A snapshot with more than 512 MiB of new bytes (small files kept from an interrupted assembly count, because they are re-hashed) is assembled in the Spark's background: the CLI polls, and exits 6 asking you to rerun if the reported progress stalls for 10 minutes. A smaller snapshot is assembled within the sync even while another snapshot is assembling in the background. Rerunning resumes: uploaded chunks are never sent again, and after a stall or a killed assembly the files already assembled are kept. A failed background assembly (a corrupt stored chunk, credential content or a full disk) discards the small files it assembled, keeping completed files over 512 MiB, and the rerun queues the snapshot again behind any others; each corrupt chunk costs one upload round. Ambiguous transport failures (exit 4) are retried up to five times (2, 4, 8, 16, 30 s) once the sync has reached the Spark; a disconnect by the owner, LAN-only refusal, authentication failure (7) or the commit request to an older controller is never retried. Every request of a sync, including each poll and upload batch, and the job submission after it, re-reads the saved connection state, so `sparkdev disconnect` stops a running sync at its next request. The paired route carries at most a 4 MiB request, so a manifest of very many files may need LAN SSH. The Spark keeps 64 GiB of its disk free, counting the bytes queued snapshots will still write. A sync whose uploads and assembly would cut into that is refused before any upload with `insufficient_disk` (exit 6, not retried; free space, then rerun), uploads are refused the same way, and a job whose work copy would cut into it stays queued with `admission_blocked`. Free and reserve figures are in `status.storage` and the `devices` Spark `storage`. Sync output adds `spark_limits`, `spark_storage`, `sync_rounds`, `materialize_polls` and `transfer_retries`.

`prepare` submits a fixed runtime-specific locked downloader, with the same job/wait/logs interface. It cannot run caller-supplied setup commands. Dependency egress uses the separately installed allowlisting proxy and fails closed if it is unavailable, independently of the 0.4.1 job-internet switch. `--runtime cuda` installs `requirements-cuda.lock` in the CUDA image without a GPU and refuses packages the image provides; `status --json` lists the Spark's `preparable_runtimes`. See the remote controller docs for registry provisioning and supported lockfiles.

## Locked system packages (0.5.0)

Use `sparkdev-system.lock` in the project root for system libraries, tools and fonts. Generate it once using the fixed helper in a **fresh scratch project without an existing system lock**, using the same runtime as the target project. The resolver accepts `NAME` or `NAME=EXACT_VERSION`; it resolves the dependency closure against the pinned base, verifies signed apt metadata and emits exact versions, URLs, sizes and hashes. Package maintainer scripts do not run during resolution. Public job internet must be enabled by the owner; do not change that policy yourself.

```powershell
New-Item -ItemType Directory C:/work/package-lock-scratch
sparkdev --client codex --json run C:/work/package-lock-scratch --where spark --runtime python --detach --request-id fonts-lock-001 -- python3 /sparkdev-system.py lock --package fonts-dejavu-core --package imagemagick --output /work/sparkdev-system.lock
sparkdev --client codex --json wait LOCK_JOB_ID --timeout 20
sparkdev --client codex --json logs LOCK_JOB_ID --since 0
# Continue wait/logs until successful completion and automatic file return.
Copy-Item C:/work/package-lock-scratch/sparkdev-system.lock C:/work/project/sparkdev-system.lock
sparkdev --client codex --json prepare C:/work/project --runtime python --request-id fonts-prepare-001
# Poll the returned preparation job to success before submitting project work.
```

Review the generated lock before deliberately replacing a project's old lock. To change requested versions or the base runtime, repeat resolution in a new scratch directory; the helper refuses resolution from an already-derived image and does not overwrite an existing output. No manual dependency-by-dependency lock construction is needed. Supported bases are Debian 12/13 and Ubuntu 22.04/24.04 on arm64/amd64; the image's distro and architecture must match.

The lock is JSON with required `v:1`, `manager:"apt"`, `base_image:"sha256:<64 lowercase hex>"`, `distro:{"id":"ubuntu","version_id":"24.04"}` (or the supported Debian equivalent), `architecture:"arm64"|"amd64"`, and `packages`. Each package requires `name`, exact `version`, HTTPS `.deb` `url`, lowercase `sha256` and integer `bytes`. Optional `requested` lists the original package requests. These digest/version descriptions are placeholders, not a usable lock. URLs may not contain credentials, queries or fragments. The generated file includes the needed dependency closure, up to 2,048 packages, 2 GiB per package and 16 GiB in total.

Preparation downloads the exact locked bytes through the guarded public proxy, then installs them in an offline, capped build container. Root is confined to that image-build step; normal jobs, dependency download and language preparation remain nonroot. The existing language-package domain allowlist remains in force for language preparation. No host apt or sudo is needed. The project-derived image is keyed by base/lock/installer identity and recorded by immutable digest. Normal runs and model services select it automatically once preparation succeeds. An unprepared or stale lock fails clearly; prepare with the matching runtime instead of bypassing it. Job status exposes `system_packages.phase`, `lock_sha256`, `base_image`, `image` and `count`. Repeating an unchanged prepared lock reuses the image.

## MCP

Start `sparkdev --client codex mcp` or `sparkdev --client claude mcp` as an MCP stdio server. It supports initialization, tools/list and connection/resources/devices/plan/prepare/run/wait/logs/status/cancel/serve/call/outputs through the same core. Inspect devices and plan placement before submission; neither reserves capacity. Run and locked dependency preparation detach; wait is bounded. Files return automatically; `outputs` only inspects metadata. Server launch arguments bind the accounting client, and tool calls cannot override it. JSON-RPC output contains no progress chatter. The transport uses newline-delimited JSON with a 2 MiB message limit. Real agent-session acceptance is separate from these protocol tests.

## Stable control exit codes

| Code | Meaning |
| --- | --- |
| 0 | Command succeeded; inspect job state for detached work |
| 2 | Invalid arguments, JSON or immutable request conflict |
| 3 | Local configuration, filesystem or process problem |
| 4 | Connection failure, dropped SSH connection or bounded transport timeout; the message says whether the request may have run remotely |
| 5 | Source/credential/path policy rejection |
| 6 | Remote operation or protocol integrity failure, including a stalled Spark snapshot (rerun to continue) |
| 7 | SSH authentication or pinned host-key failure; no fallback |
| 8 | Laptop admission or worktree claim conflict |

Attached workload exit codes take precedence and may overlap control codes. Distinguish them through `process_exit_code` versus `{ok:false,code,message}`.

## Copy-paste agent instructions

For AGENTS.md or CLAUDE.md in a project that uses this utility:

> Offload Linux-capable builds, tests, renders, media and compute through sparkdev by default. Use your actual client label (`codex` or `claude`), `--json`, `run --where auto --detach` with a retained request ID, bounded `wait --timeout 20`, and incremental `logs --since OFFSET`. Check `devices` and `status --all` first. Files return automatically: wait through `returning`, inspect the final workload exit code and `returned` receipts; `outputs JOB` is optional inspection, not a required fetch. Preserve conflict copies and recovery backups. Write deliverables under `/sparkdev-output` when they should land in local state/results/JOB. Use `--no-return` only for deliberate opt-out. GPU Python needs `--runtime cuda`; direct ffmpeg/blender infer it. Keep Windows installers/tests local through the configured build gate. Never claim another agent's label as acceptance evidence, change owner policy, run owner-only discover or weaken host verification. Reuse retained request/job IDs after an interruption. Use the documented system-lock resolver and prepare workflow for libraries/fonts; never host apt/sudo.

Codex requires process-launch permission for the installed executable and SSH/paired-link network access. In restricted environments allow those capabilities explicitly through the environment's existing controls; never weaken SSH identity verification. The owner's present session is unrestricted, which does not prove behavior in a different Codex sandbox.


Automatic address learning can be disabled or restored explicitly:

```powershell
sparkdev --client human --json connection --auto-addresses off
sparkdev --client human --json connection --auto-addresses on
```

`transport.lan_path` reports `kind`, `speed_mbps`, `faster_unanswered`, `cable_elsewhere`, and `shared_network`. When Spark cable and Wi-Fi share a subnet, Linux can still carry traffic over Wi-Fi; turn off Spark Wi-Fi for a meaningful cable-only throughput check. `devices.laptop.network` separately reports the Windows interface selected for the actual LAN destination, its description and transmit link rate. Unknown interface/rate values remain null. These read-only Windows API observations omit SSIDs and MAC addresses. A USB adapter description is only a hint: DGXBridge does not infer the negotiated USB generation or measured transfer speed from it.
