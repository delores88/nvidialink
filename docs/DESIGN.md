# DGXBridge design

Status: implementation contract, 2026-10-13. Product name DGXBridge; repository nvidialink; CLI `sparkdev`.

## Evidence and boundaries

Read the Spark Link protocol, GPU placement document, SSH prototype and physical Spark probe before this design. Upstream reference is PhaseForge `ac30e04` on `claude/0.25-spark-p2`; the local checkout has advanced, so use git show/archive at the pinned commit. The protocol describes QR owner linking after SSH, endpoint-key authenticated iroh, short-lived approval tickets, and jobs.v2 content-addressed chunk transfer. GPU placement documentation still contains historical 0.21 capability statements: implementation at the pinned revision wins when they differ.

The new repo initially contains only README and MIT license. SSH was verified with BatchMode, StrictHostKeyChecking=yes, HostName 192.168.0.226 and HostKeyAlias 192.168.1.186 through tuningspork-spark. Spark reports aarch64, 20 cores and about 120 GiB RAM. Existing Spark Link and owner containers remain untouched. Local D: space is constrained; build output uses C:.

## Components

1. A Rust `sparkdev` binary/library owns CLI parsing, exact argv, project inventory, SHA-256 CAS upload, transport selection, local receipts and detached job interaction. Desktop calls the same binary with structured JSON; it does not interpret shell commands.
2. A Tauri desktop app provides SSH setup, connection health, QR pairing, linked Spark and job views. Its Windows executable carries a real multi-resolution ICO and Start-menu shortcut. Setup reuses existing SSH key references without reading or copying private key material.
3. A Python standard-library remote controller, separately installed under `~/sparkdev`, handles validated JSON RPC on stdin/stdout through SSH and the authenticated iroh adapter. A separate user systemd service schedules jobs and reconciles Docker containers after restart. SQLite transactions persist manifests, immutable job requests, fairness, cancellation and audit records. Docker owns detached workload lifetime; losing the connection or restarting the controller does not restart a job.
4. An independent Rust iroh bridge reuses pinned Spark Link protocol/pairing primitives with provenance, separate identity, ALPN, UDP/LAN ports and state. It never joins or controls the existing PhaseForge Spark Link service. Owner pairing starts only over pinned SSH. A QR opens the Spark LAN approval page; approval authorizes the desktop endpoint. Remote endpoints remain pinned and fail closed. Relay configuration awaits verified owner deployment details.

## Wire contract (version 1)

Each RPC is one JSON request and one JSON response. Requests include `v:1, op, ...`; responses include `ok` and structured error `code,message` on failure. Operations: `doctor`, `status`, `missing` (hash list), `put` (sha256, base64 chunk), `sync` (project, manifest), `run` (project, manifest_id, argv, runtime, client, request_id), `wait` (job, timeout capped 60), `logs` (job,since,limit capped 1 MiB), `cancel` (job). `run` persists request_id before container creation and rejects different content reusing a request_id. Request IDs are generated and saved locally before network submission; explicit `--request-id` allows recovery. Logs use byte offsets; responses carry `next_offset`, state and exit_code. Errors do not echo input contents. Remote helper command is fixed, never built from user argv.

Manifest entries: `{path,size,sha256,mode}`; project ID is SHA-256 of canonical local project path (distinct worktrees isolate caches). Manifest ID is SHA-256 of canonical manifest JSON. Chunk upload uses SHA-256-addressed objects, 1 MiB maximum chunks and per-file chunk lists for resumable large inputs. Server validates all hashes, sizes, paths, limits and materializes into immutable snapshots before execution. No tar extraction.

## Sync and secret policy

Inventory uses `git ls-files --cached --others --exclude-standard -z` within a Git project, with a safe walk fallback for a plain directory. Deny `.git`, target, node_modules, dist/build caches, symlinks/reparse points, paths outside root, secret directories, credential/key extensions and names. Scan file content for private-key headers and recognizable credential patterns; reject rather than print contents. Tracked ignored secrets are still rejected. Perform full policy validation before any upload. Persist CAS objects atomically; changed/deleted files produce a new immutable snapshot.

## Runtimes and resource isolation

Owner-installed registry contains only named Rust, Node, Python and optional CUDA runtimes pinned to immutable Docker digests/image IDs with provenance. Callers select a name, never an image, flags, host path or entrypoint. Use independent `sparkdev-*` container/network/volume names. Docker jobs: read-only root, nonroot user, cap-drop ALL, no-new-privileges, bounded tmpfs, pids >=512, memory and swap capped, CPU total <=16, nice priority 10, network none, no host/docker socket or other project mounts. Default memory headroom is at least 32 GiB. GPU jobs additionally require a MemAvailable watchdog because GB10 CUDA memory is not reliably bounded by cgroups.

Scheduler admission caps total 16 CPUs and 64 GiB across jobs, per-client concurrency 2 and CPU 8 (claude/codex/human); FIFO rotation between clients. Initial real validation uses smaller caps to avoid disrupting Claude. Per-project caches are locked for writing so different worktrees can run concurrently without cross-project pollution.

Dependency preparation is a separate fixed operation with lockfiles enforced: cargo fetch --locked, npm ci with package-lock, pip --require-hashes. Network is permitted only through an allowlisting HTTPS CONNECT proxy (crates.io/static.crates.io/index.crates.io, registry.npmjs.org, pypi.org/files.pythonhosted.org and specifically GitHub release asset hosts). Execution stays network-none. No unrestricted `--net` escape hatch. Until this path is verified, fetching fails closed and offline cached jobs remain possible.

## CLI and desktop

Commands run/sync/status/logs/cancel/doctor plus wait/setup/pair. Global --json, --client; run --detach, --runtime and --argv-json. Run passes through workload exit code; documented control failures use stable reserved codes. JSON mode returns structured messages; all captured output is saved in owner-local application state. `run --detach` returns after admission, `wait --timeout` stays bounded, logs are offset-idempotent. Pending cancel is persisted locally and retried on the next authenticated connection. SSH uses BatchMode, no TTY, no agent/password prompts and strict host pinning. LAN connection attempts are bounded; status reports the selected path and reason. An unconfigured or unpaired remote path is explicit, never substituted with insecure transport.

### Connection lifecycle

Persist `connection_mode` as `lan-only`, `remote-only`, or `both`, and `connection_enabled`. Migrate absent fields from the old `allow_remote` flag and connected default. LAN-only uses strict pinned SSH; Remote-only skips SSH and requires the existing authenticated paired transport; Both tries LAN first and falls back only on reachability failure, never host-key/authentication rejection. A paired route does not establish whether traffic is direct or relayed. Report observed routing and unavailability honestly.

LAN rediscovery orders candidates as follows. An address that already authenticated in this process is tried alone. Otherwise the order is remembered verified addresses (max 4, newest first), configured hosts, then the alias's concrete `HostName` from a local, network-free `ssh -G`. Remembered addresses only reorder that current set (case-insensitive); an address that is no longer configured or the alias's `HostName` is never dialed, so changing the hosts takes effect at once although the binding below omits them. With configured hosts the bare alias is never dialed, as before rediscovery. Every candidate is then a concrete, deduplicated address, so a win is sticky and remembered, and a label alias is never resolved by DNS to an unrelated server. Without configured hosts the plan is exactly the alias, as before. Configured hosts are never truncated; the alias `HostName` is added only below 8 candidates.

When more than one candidate is planned, concrete addresses get a parallel TCP precheck of the SSH port (1.5 s per connect, 2 s overall; DNS also counts against the deadline). A plan of one candidate is not prechecked: nothing could be dialed ahead of it, so a check could only add its own time to the dial it had before rediscovery. Each probe runs on a detached thread and reports over its own channel. Results are consumed in planned order with a bounded wait, and nothing joins the probes, so a request returns as soon as it has its answer: a live early address never waits for a dead later one, though a dead earlier address still costs up to its own check. A probe is `Open`, `Closed` (refused, or silent for the full connect budget), `Unresolved` (the lookup finished empty) or `Unchecked`. `Closed` and `Unresolved` hold a candidate back rather than drop it. A held-back configured host keeps its place ahead of later candidates for every failure that ran nothing remotely: before a later candidate's rejection or other pre-authentication failure ends the request, and before giving up, each held-back configured host gets one dial in planned order, and the first of them whose own failure ends the request decides it, as the earliest host did before rediscovery. So a precheck false negative (a first SYN or ARP over 1.5 s, a flaky resolver) never lets a later host's refusal end a request the earlier host could have served; a failure after authentication, or a timeout, at a later host still stops at once. That dial uses `ConnectTimeout=3`, what the 2 s deadline left of the 5 s the host had before rediscovery, so the precheck plus the dial never cost a dead host more than its one dial did. A held-back alias `HostName` outside the configured hosts is not dialed. When nothing answers, the cost is at most the serial dials the code made before rediscovery plus the local `ssh -G`. A probe that runs out of time, whether in a slow lookup or a connect cut short by the deadline, is `Unchecked`, and the address is dialed in order with OpenSSH's own budgets. An alias with ProxyJump, ProxyCommand, BindAddress or BindInterface, or a failed `ssh -G`, prechecks nothing: ssh reaches every candidate as `-o HostName=<host> <alias>`, so through the alias's own route, and a direct local check would test the wrong path. The precheck is a reachability hint, never trust.

Every dial uses the unchanged pinned command: BatchMode, `StrictHostKeyChecking=yes`, `HostKeyAlias` and no password prompts, never `accept-new` and never a known_hosts write. It also sets `LogLevel=VERBOSE`, at which OpenSSH writes "Authenticated to <host> ... using ..." (or "(via proxy)") to stderr once user authentication succeeds and before it opens the session that runs the command. stderr is only classified, never shown or stored. Authentication and host-key markers are a rejection at any exit code. Unreachability and drops are read only from OpenSSH's own exit 255; a remote command's own exit status is a command failure whatever it printed, since `sparkdev-link` or the controller may print "Connection refused" themselves. The authentication line or any stdout proves the session phase and can only push a result toward it, so text written by the remote never reads as a handshake drop. An ssh exit 255 with no stdout and without that line ended before authentication. Without that proof a drop is still a handshake drop only when OpenSSH tagged it with the identification exchange (`kex_exchange_identification`, `ssh_exchange_identification`, `banner exchange`) next to a reset, close, abort or broken pipe. OpenSSH prints the untagged "Connection reset by <ip> port <n>" and "Connection closed by <ip> port <n>" from one template in every phase, so those, a lost session ("closed by remote host", "Read from remote host", `client_loop`, a server-alive timeout, a corrupted MAC or bad packet length) and "Connection to <host> port <n> timed out" are session drops: the command may have run. Observed on loopback with OpenSSH 9.5 (Windows): a reset before and after the banner gave the untagged form, a reset after authentication followed the authentication line, and a stalled key exchange or authentication exited 255 after about 10 s (`ServerAliveInterval` x `ServerAliveCountMax`). A tagged message with a refusal or timeout is unreachability (a ProxyCommand that could not connect, a banner timeout), and a tagged one without a broken link, or "Unable to negotiate", is an incompatible server.

A request repeats at most one dropped dial in total, at the same candidate, with the identical command and request bytes, after 1 s plus up to 499 ms of jitter. A handshake drop is repeated for any request. A session drop is repeated only for a controller request that is idempotent there: `missing`, `put`, `put_many`, `sync`, `status`, `logs`, `wait`, `doctor`, `cancel`, `heartbeat`, `release`, `resources` without `limits`, and `run`, `prepare` and `claim` with a non-empty string `request_id`; the allowlist refuses anything else, raw desktop commands included. The request deadline is taken before planning and the precheck, one dial's process timeout after the start. After any drop, every later dial's process timeout is clipped to it, and neither the repeat nor another candidate is dialed with less than 10 s, plus the server-side wait the request asks for (plus the backoff, for the repeat), left. Rejections, timeouts and process errors are never repeated. Retrying more than once is deliberately not done: two drops in one request mean the link is bad, and the honest result is an error. Each dial, repeat included, gets one `attempted_routes` record; a drop's record carries `phase`, `try` and `retry`.

Once any try at a candidate dropped in the session phase, the request ends at that candidate: 7 for a rejection before authentication, otherwise 4 with a fixed message that says the request may have run remotely and whether it is safe to repeat; run and prepare append their request ID. It never moves to another candidate, never falls back, never forgets the address and never changes the sticky host. This applies to the alias `HostName` outside the configured hosts too, because the command may have run there. A handshake drop ran nothing and moves on, keeping a remembered address: a reset on a flaky link is no evidence that the address is stale. When nothing else serves the request it ends with the fallback-eligible "SSH connections to the Spark dropped during the handshake, before authentication; nothing ran remotely. The network link looks unstable.", so the paired transport may still serve it. Before authentication, reachability failures continue to the next address. A candidate the code before rediscovery dialed (a configured host, whatever its source, or the alias when no hosts are configured) keeps that code's failure semantics unless it is remembered: authentication or host-key failure returns 7 with no further candidates and no fallback, and an incompatible server or another pre-authentication failure returns 4, in both cases after the held-back configured hosts ahead of it got their dial. A remembered address is a learned hint. It is forgotten, and the next candidate dialed, only when it rejects the host key or login or answers with an incompatible SSH server; a drop or a timeout never forgets it. Nothing ran remotely, so this cannot duplicate work. A rejection at a remembered configured host still refuses fallback: unless another candidate authenticates, the result is 7. The alias `HostName` outside the configured hosts was never dialed before rediscovery, so any failure there that ran nothing (remembered or not; a rejection, an incompatible server, a handshake drop, too many authentication failures, or a transport timeout whose complete stderr lacks the authentication line) is recorded and the next candidate dialed, and it never turns an otherwise unreachable result into 7. A killed ssh's stderr counts as complete only when its pipe closed within 500 ms; a ProxyCommand that holds it leaves the timeout unknown. Post-authentication failures, other timeouts and process errors stop at once for every source: the pinned Spark was reached, or the command may have run. "Configured LAN addresses are unreachable" and the handshake-drop message are the only fallback-eligible errors. Every LAN attempt's `target_index` is the dialed address's position in the configured hosts, whatever its source, and an authenticated route reports the dialed address as `lan_host`, which the GUI shows as the address used.

A concrete address that authenticates is remembered in owner-local `lan-route.json`. Entries are bound to a SHA-256 of alias, pin, port and user. The file holds 8 entries, 4 per binding, each expiring 30 days after its last verification. A head verified more than a day ago is rewritten on its next success, and timestamps more than five minutes in the future are ignored. Remember and forget share one write path. It writes only when diagnostics report the state folder is not redirected; unknown counts as redirected, and a skipped write creates no lock file. Automatic rediscovery never edits `config.json` and never scans subnets; Find my Spark, below, is the only search and runs only on the owner's request.

Connect enables the saved route and checks it. Disconnect prevents new requests and admissions without deleting credentials/pairing or cancelling jobs. Already admitted independent jobs continue; an existing laptop worker retains its admitted transport snapshot for lease heartbeats. Fresh CLI/MCP processes honor the saved disconnected state. Configuration remains editable while disconnected; SSH bootstrap is a separate deliberate operation, not a prerequisite to every Connect click.

### Find my Spark

An owner-only, on-request search for the pinned Spark on this laptop's own network. The CLI `discover` command runs only with exactly one explicit `--client human` token before any `--` (so a duplicate global flag that clap resolves to human is still refused); the desktop allows it in its existing `cli` command and refuses a save during phone pairing; it is no MCP tool. Nothing automatic runs it: not devices, status, connect, the refresh timer, F5 or the "Configured LAN addresses are unreachable" error, which only highlights the button. An address becomes dialable only through the owner's explicit Save into `config.hosts`; found addresses are never dialed on their own.

Adapters come from GetAdaptersAddresses (IPv4, with gateways): up, IfType 6 or 71, not a tunnel, a non-zero IPv4 gateway, GetIfEntry2 HardwareInterface and ConnectorPresent set and FilterInterface clear, and unicast addresses whose DAD state is Preferred and that are RFC 1918. Each network is clamped to the laptop's own /24 or narrower, beyond /30 is skipped, identical networks merge keeping every adapter, and at most two are searched. A target stays only when GetBestInterface sends it out of one of its network's adapters, so a VPN routing private ranges never carries the sweep. The sweep is the existing parallel precheck at 3 s per connect inside 4 s on the configured port. At most 32 open addresses (configured, alias HostName, then ascending) get the unchanged pinned `Transport::command` running `true`, 16 at a time, 8 s each; `ssh_raw` is never used. An alias that is not direct refuses the search.

Each check is classified from its exit code and stderr, first match wins: exit 0 verified; "remote host identification has changed" or "has changed and you have requested strict checking" another host; "bad owner or permissions", "bad permissions", "unprotected private key" or "load key" a local key error; "permission denied (" or "too many authentication failures" a refused login; "host key is known for" or "host key verification failed" an unknown key; anything else unverified. The pin is proven only by a verified check or a "permission denied (" reply. A changed key is reported as another host only when the pin was proven in the same run, because a missing or rotated pin makes OpenSSH print the same failure for the Spark itself; otherwise it is an unknown key, and a configured or alias address with an unknown key sets `pin_hint`. Other devices appear only as counts, and unchecked probes are counted so that "nothing found" is not overstated.

Save refuses unless diagnostics report `redirected` exactly false, needs a private IPv4 address inside a current network and routed through it, and checks it again in one wave with up to 15 configured IPv4 addresses on those networks. Only a verified address is saved. Under `config.lock`, the `update_config` change first compares alias, pin, port, user, key file, connection and mode with the configuration that was checked and writes nothing if any differ. Otherwise the canonical address goes first, the fresh hosts follow, and only configured addresses this run proved to be another host are removed; closed, unverified and unknown-key addresses are kept, so an unplugged wired address survives. With no hosts before, the alias is appended only when the raw `ssh -G` hostname line echoes it. The address is then remembered best-effort in `lan-route.json`.
