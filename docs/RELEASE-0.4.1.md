# DGXBridge 0.4.1

Status: published and installed on 2026-10-21, then rejected by Marketplace scanning for high/critical Pillow vulnerabilities. This immutable release remains available for provenance; use the 0.4.2 replacement. Final Windows and ARM64 builds, package identity checks and the physical Spark checks below are recorded.

## Changes

- Clearer connection and resource controls, confirmed internet-setting readback, saved-download usage and limits, and named model-service status. Job history and fetched logs remain visible when the connection drops. Claude Code and Codex each get a copyable prompt with the selected connection and owner-state references.
- Authenticated Spark route learning prefers recent verified wired links. Connection details distinguish the Spark's link from the laptop's adapter and warn about a known slow laptop link. Reported link rates are not measured transfer speeds. Finding an unknown Spark remains an explicit owner action.
- New Spark jobs can use a public HTTP/HTTPS proxy when the owner's internet setting is enabled and helpers are available. Turning it off cuts running internet helpers. Direct external sockets and tools that ignore proxy settings are unavailable. CONNECT tunnels can reach any permitted public destination port; their payloads are not inspected or restricted to HTTPS. An enabled setting does not prove connectivity or a successful download. Locked dependency preparation retains its package-host allowlist.
- Saved downloads survive individual jobs and result-cache bypasses. Owner controls manage their space limit and queue clearing while jobs are active. Shared downloads are writable by other jobs in the same owner trust domain; they are not isolated against a malicious job. Do not store credentials there or treat a cached model as inherently trusted.
- Named HTTP model services support retained requests and replies through the authenticated bridge. They use the supplied model adapter and weights, expose no public listening port, and have startup, idle, lifetime, request and reply limits. This is not a general browser-facing or streaming model API. See [SERVERS.md](SERVERS.md) for the consumer contract and limits.

## Verification recorded so far

- The UI's 27 model tests pass. Isolated browser fixtures at 1140px and 850px cover layout, setting readback, stale-response protection, retained logs, services and download controls. These use a synthetic backend, not the installed desktop app.
- Actual Codex-submitted Spark jobs passed 219 Rust workspace tests and 291 Python controller tests; the ARM64 builds succeeded. The full Python run predates the small HTTP request-framing fix in `c9cae0f`. After that fix, 27 focused proxy/guard tests passed locally, followed by successful physical HTTP and HTTPS requests. The full Python suite was not rerun after that change.
- The final gated Windows build passed 219 workspace tests and 26 desktop tests, built the Windows binaries and produced the NSIS installer. Local Cargo used the unchanged PhaseForge build gate.
- Physical Spark runtime provisioning completed CPU and CUDA probes. A pinned SSH connection reported a 1,000 Mbps Spark wired link and a separate 100 Mbps laptop wired link. These are interface rates, not measured throughput between the laptop and Spark.
- On the physical Spark, a fresh Python job passed 19 checks: public HTTP/HTTPS returned 200; observed-public-address literal and DNS destinations, private networks, Spark addresses and metadata were refused; direct protected TCP, external DNS and job IPv6 were unavailable. A fresh CUDA job passed package-install and cross-runtime shared-cache checks. These used the installed CLI over pinned LAN SSH, with client `codex` and result caching disabled.
- A public model shard of 4,972,489,328 bytes was downloaded and SHA-256 checked in 81.629 seconds. A distinct project's fresh job reused the same cached file and inode with `local_files_only`, including a full hash check in 2.504 seconds. This proves large-file transfer and cache reuse; only one shard was fetched, with no model inference performed. The measured transfer was internet-to-Spark, not laptop-to-Spark.
- A Python standard-library HTTP service on the physical Spark passed repeated-start identity, retained-reply hashes, same-request deduplication and explicit-stop checks through a candidate Windows CLI over LAN SSH. A later paired-transport service check also passed retained-reply and deduplication checks after an earlier status attempt timed out. The paired path was not classified as direct or relayed and was not a hotspot test. Neither service used model weights.
- A physical GB10 check allocated a 16 GiB CUDA tensor despite an 8 GiB container memory limit. It was explicitly stopped and cleanup was confirmed. CUDA memory therefore cannot be described as bounded by the Docker memory cap; the host-memory watchdog remains necessary, and its pressure-kill behavior was not exercised by this check.
- The physical owner internet-off check removed the proxy during an active HTTPS stream, after which reads timed out before completion. A fresh offline job succeeded with external DNS and direct TCP blocked. The exact prior default-on policy was restored, resource limits remained unchanged, and the audit chain was verified.
- Packaging checks passed 12 tests with one skip. All five SBOMs are nonempty and match their binary hashes: Windows GUI/CLI/link and Linux ARM64 CLI/link. The GUI inventory describes the NSIS-marked executable, and the installer-content proof finds that GUI plus both Windows sidecars. The notices inventory contains 449 packages; all 806 referenced license texts match their recorded hashes.

The candidate installer `DGXBridge_0.4.1_x64-setup.exe` has SHA-256 `9e9e0b1beb762cf8d92ba8bad3b1f2ca9435a49ec5bfc25b2fe35e522aaeeb40`. This is a package identity, not evidence of publication, installation or Marketplace admission.

## Limits and pending acceptance

The internet guard denies private networks, Spark host addresses and cloud metadata. It also targets the public IPv4 address observed by its own helper and closes connections if that observation changes, expires or fails. Checks are periodic, not instantaneous. Other public router aliases or addresses reached through different routing policies may remain undiscovered. The physical checks cover the tested destinations; they do not establish that every route into a home network is blocked.

An ordinary Windows Explorer in-place upgrade installed the exact candidate in the physical owner profile. Installed GUI and both sidecar hashes match the package; configuration and pairing hashes were preserved. Six bounded native checks passed: live status, paginated history and fetched logs, saved resource/download readback, connection layout, both agent setup tabs and the updater drawer. See `evidence/dgxbridge-041-windows.json`. A fresh updater download/install cycle was not exercised. Publication completed, but Marketplace rejected this version. Remote/hotspot use, sleep/disconnect recovery for this candidate, real model inference or TTS latency, watchdog pressure killing and actual Claude Code invocation have not been established by these receipts. Source tests, physical Spark runs, installation and Marketplace admission remain separate evidence layers.

DGXBridge is an independent application with MIT first-party source and preserved third-party notices. The Windows application is unsigned; it is not an NVIDIA product or an NVIDIA-signed installer. Publication is intended as an ordinary, nonfeatured Marketplace listing, with PhaseForge remaining featured.
