# Privacy and local state

DGXBridge uploads selected source files and exact job arguments to the owner's Spark. It stores content-addressed source snapshots, per-project build caches and prepared environments, request receipts, combined process output and a job audit trail, shared model/package downloads and named HTTP service request/reply payloads. The desktop/CLI retain configuration, job receipts, log chunks, saved replies and pending cancellations in the owner's application state directory. The 0.5.0 candidate also retains result manifests, original source paths/hashes, resumable transfer staging and automatic-return receipts there. There is no telemetry or embedded model-provider account.

`lan-route.json` there stores verified LAN addresses for the paired Spark only: at most eight, each expiring 30 days after it last authenticated, keyed by a hash of the SSH alias, pin, port and user. It only reorders addresses the current configuration already names. It is never uploaded.

Find my Spark runs only when the owner asks. It sends one TCP connection attempt per address to the SSH port in this laptop's own /24 network (at most two networks, never through a VPN route). A device that answers sees that connection and, for the pinned check, the SSH banner and key exchange; the login is attempted only after its host key matches the pin, so other devices never receive a login attempt. Results stay on this laptop: other devices are reported only as counts, and nothing is stored unless the owner saves an address, which then goes into `config.json` and `lan-route.json`. Endpoint security software or tools such as fail2ban on the network may notice the connection attempts.

The SSH private key remains with OpenSSH. The app stores its path, not its contents. A separately generated link device identity is encrypted for the Windows user using DPAPI; Linux state is owner-readable only. Pairing tickets, QR tokens and six-digit approval codes exist only during the approval workflow and must not appear in screenshots, release evidence or logs.

Every `status`, `doctor` and `devices` request also carries the Spark's network link report, which agents receive like any other client. On each request the controller reads bounded sysfs and procfs files and, when its link is Wi-Fi, runs `iw` or `nmcli` at fixed paths. It never scans for networks and never requests SSID or BSSID fields, and raw tool output is discarded after parsing. The report holds no SSID, BSSID, MAC or IP address: interface names derived from a MAC address (`enx…`, `wlx…`) are replaced by aliases such as `usb-ethernet-1`. It contains interface names, link kind, carrier, speed, driver and radio band, channel, bitrate and signal.

In the 0.4.1 candidate, normal Spark jobs have public internet access by default through a per-job HTTP/HTTPS proxy. It blocks home/private addresses, the Spark, cloud metadata and IPv6 destinations; direct raw TCP/UDP access is unsupported. Each public helper sends a fixed credential-free HTTPS request to api.ipify.org to observe its outbound public IPv4, which it also blocks to prevent access through that observed address's router forwards or hairpin paths. The service sees the helper's public IP and ordinary connection metadata; the check sends no project files, job arguments, credentials or model data. Startup requires a successful check; checks repeat every 30 seconds, observations expire after 60 seconds, and failed checks or changed addresses cut established proxy tunnels. Additional router public aliases and addresses used by different outbound routes are not discovered. New global host/on-link addresses, or an unreadable network snapshot, stop affected helpers when observed by the scheduler; this is not a zero-delay network-change guarantee. The owner may turn internet off, including cutting helpers for existing jobs at the next scheduler tick. A job can send its data to public sites: the private-address guard is not a data-loss prevention system. HTTPS CONNECT preserves upstream TLS; CONNECT payloads are opaque and are not restricted to an application protocol. Plain HTTP remains plain HTTP. Direct sockets and unproxied external DNS are unavailable; a job may tunnel another protocol through an allowed public CONNECT destination. Proxy counters retain integer usage totals, not URLs, request bodies, cookies or authorization headers. Explicit dependency preparation keeps its separate domain-limited public-package proxy. Optional encrypted iroh relay traffic exposes connection metadata to relay operators; it does not give them the device keys or plaintext job content. The public relay option must be selected by the owner. No private owner VM is bundled or presumed to exist.

Source, job records and logs persist until the owner removes the bridge's own state; they have no general automatic retention cleanup. The saved-download cache is one trust domain writable by every job, even jobs with internet disabled. It can contain model names, downloaded files and library cache metadata. Tokens and executable model/extension caches are directed to private per-job paths; do not override these defaults or put secrets in `/cache`. Automatic cleanup removes eligible old downloads only while jobs are idle; an owner-requested clear waits for running jobs. Per-job disk temporary files are removed after their container stops. Model-call body/reply files become eligible for cleanup at the earlier of completed delivery plus 10 minutes or creation plus one hour; idempotency metadata becomes eligible 24 hours after creation. Actual deletion requires successful controller housekeeping, so a stopped or delayed controller or cleanup errors can extend on-disk retention. Saved laptop replies remain until the owner removes them.

By default, Spark batch jobs return new/changed regular files from `/work` into the originating laptop project and files from `/sparkdev-output` into local state under `results/JOB`. This can write project files after the submitting agent exits. The Windows installer registers the detached return worker at user logon; it uses the existing owner state and authenticated connection. It resumes pending work when the laptop is awake, signed in and connected. Updates stop the return worker to replace its executable while preserving its receipts, configuration and admitted jobs. `--no-return` opts out per run. No additional model-provider login is involved.

The physically checked `%USERPROFILE%/.dgxbridge/return-workers.json` records only worker-executable and owner-state directory paths, including custom state locations. The ordinary installer owns the single logon registry entry; packaged CLIs write no startup registry entries. The logon dispatcher resumes only records matching its own executable and passes each state path explicitly, refusing missing/redirected configuration rather than creating another identity. Uninstall removes the logon entry and retains this path list for reinstall, alongside the existing owner state.

Before replacing an uploaded original, the return worker checks that the laptop file still matches its uploaded hash. Newer edits stay intact and the returned file is written as a `.spark-JOBID` sibling. A safe replacement can also retain a hidden `.name.spark-original-JOB-UUID` backup; the current implementation does not delete those backups automatically. Remote deletions are not applied locally. Returned files, conflict copies, backups and receipts have no automatic local expiry. Cache/control folders and credential paths are excluded, and links/unsafe paths are refused; recognizable secret scanning cannot detect every unknown secret format.

Frozen Spark result copies are limited to 64 GiB per file/per job, 10,000 files and a 3 MiB manifest. Unacknowledged results have seven-day retention; after every receiver acknowledges the exact hash-verified manifest, retention becomes one day. Cached-result admissions can extend expiry. Inspect `outputs.retention.expires_at`; expiry makes files unavailable and eligible for subsequent housekeeping, not guaranteed deleted at that instant. This expiry does not remove original source snapshots, job work directories or logs. Disconnected clients cannot receive expired result copies without rerunning the workload.

An optional project `sparkdev-system.lock` contains package names, exact versions, public HTTPS URLs, byte sizes/hashes, distro/architecture and the pinned base-image digest. Resolving it contacts signed official apt repositories through the existing guarded public job proxy. Preparation downloads only locked package bytes through a guarded public proxy, then installs them offline in a capped build container with root confined to that step. The language-package allowlist remains separate. The resulting project image digest and lock identity are saved on Spark and reused; jobs run nonroot. Do not put credentials in package URLs or locks. Source tests of 0.5.0 return/retention/system-package behavior do not establish installed Windows or physical Spark acceptance.

Uninstalling the Windows application does not delete retained jobs, local pairing identity, Spark services or Spark state. Never clean PhaseForge, Ollama or another application's files when removing this utility. Do not submit secrets in source, argv, model calls or program output: the sync/call filters reject recognizable credential patterns but cannot recognize every secret format. Physical 0.4.1 download, token-placement and model-call retention checks are separate acceptance work, not implied by source tests.

The local runner launches native owner processes and is not a sandbox. Spark jobs use restricted Docker containers; a user with access to the Docker daemon already has powerful host privileges independently of this app. Device pairing and SSH enforce owner access, while client names such as claude and codex are accounting labels, not separate security principals.
